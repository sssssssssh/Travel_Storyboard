## 一、结论（一句话）

**视频功能确实开启了**（不再报"上限 0"），但**第一个视频请求就把服务打挂**：
先 `503 upstream connection termination`，随后持续 `503 no healthy upstream`，
**3 分钟内未自愈**。整个服务（含文本）当前**不可用**。

## 四、503 的两种含义要分开

1. **第一次** `connection termination`（首个视频请求）：
   上游进程在处理视频时**主动断开或崩溃**。这是**视频处理路径**上的故障，
   可能是：模型加载视频 processor 时 OOM、vLLM 版本不支持视频导致 worker 崩溃、
   或多模态权重/processor 缺失。
2. **后续** `no healthy upstream`：
   网关在上游崩溃后**找不到健康实例**。这是**结果**，不是原因。

⚠️ 按任务书 §5.1 与 AGENTS.md C8：**503 只能证明上游不可用，不能说明模型不支持视频**。
本轮**没有**得到任何关于"模型是否理解视频"的证据。

## 六、需要服务端排查的（按优先级）

1. **查看部署实例日志**：首个视频请求时 worker 是否崩溃？是否有 OOM / traceback？
   这是唯一能定位根因的证据。
2. **该 vLLM 版本是否支持视频输入**：
   `--limit-mm-per-prompt video=1` 被接受，不代表该版本实现了视频处理。
   早期 vLLM 只认 image；若版本不支持 video  multimodal，worker 可能直接崩。
3. **多模态权重/processor 是否完整加载**：视频需要对应的
   `video processor` 与模型配置；缺失时 worker 通常启动后崩溃。
4. **实例规格**：视频解码占显存/内存，规格不足会 OOM。
5. **先让服务恢复**（重启部署/实例），再复测。

## 七、恢复后的推荐验证步骤（每步 1 次请求）

1. 纯文本 → 期望 200（确认服务已恢复）
2. **1 个极短视频**（1 秒、更小体积）→ 看是否仍然 503
   - 若也 503 → 是视频**能力**问题（版本/权重），非体积问题
   - 若 200 → 是**资源**问题（大文件 OOM），需调实例规格
3. 通了再跑完整阶段 B（3 轮随机时序 + 2 个负对照）
